**Diagnosis (with evidence):**

**User-visible fix attempts that DID NOT work:**
1. `blueutil --disconnect` — re-bonds instantly
2. `blueutil --unpair` — re-bonds instantly
3. Ring on/off, app disconnected, phone BT off — no change in advertisement behavior

**Fix paths to try in the next session (priority-ordered):**

1. **System Settings → Bluetooth → right-click SR16 → Forget This Device**, then re-pair (if needed) explicitly through macOS Bluetooth settings, **not** the phone. Once fresh, the ring will advertise again and bleak can see it. REPAIR ONLY if necessary — once forgotten, the ring should advertise in normal pairing mode. Time: ~5 min.

4. **Reboot Mac:** clean slate. Time: 2-5 min for it to come back, plus re-pair overhead.

**Recommended first attempt:** path #1 (Forget via System Settings). If that fails to make bleak see the ring, fall back to #2 (PyObjC).

## New architectural decisions (session 3)

### 1. analyze.py is producer-agnostic
`analyze.py` only cares that rows exist in `hr_readings` with `analyzed_at IS NULL`. Whether they came from `hr_live.py` (real BLE), `history_sync.py` (vendor RE), `history_ingest.py` (file import), or a synthetic test insert — it doesn't matter. This means the gateway is **unblocked by the BLE-blocker**. As soon as *any* source writes hr_readings rows, the analyzer picks them up.

### 2. analyze.py is idempotent via the `analyzed_at` column
Re-running on already-analyzed rows is a fast no-op (partial index `hr_readings_unanalyzed` finds the new ones). Cron can run at high frequency safely.

### 3. Ollama model is pinned
Per USER profile (memory), the Twitter-HERETIC model is the user's local default. analyze.py defaults to `Qwen3.5-9B-Claude-4.6-HighIQ-HERETIC:latest` and accepts `--model` to override. **Never** substitute Ministral without an explicit user direction (memory rule).

### 4. Cron is `no_agent=true` + `deliver='telegram'` (silent-watchdog pattern)
Script decides whether to emit output (silent when idle, summary when new). No LLM tokens per cron tick. Telegram receives only when there's something to say.

## Protocol notes (lifted from tahnok/colmi_r02_client — Apache-2.0 ported patterns)

**Transport: Nordic UART-over-BLE** (same UUIDs as Colmi R02):

```
service: 6E40FFF0-B5A3-F393-E0A9-E50E24DCCA9E
  RX   : 6E400002-B5A3-F393-E0A9-E50E24DCCA9E   (we WRITE here)
  TX   : 6E400003-B5A3-F393-E0A9-E50E24DCCA9E   (we SUBSCRIBE here)
```

**Packet format: 16 bytes, exact:**

```
byte 0       = command (0x15 = HR log, 0x01 = set_time, 0x03 = battery, ...)
bytes 1..14  = sub-data (≤14 bytes, command-specific)
byte 15      = checksum = sum(byte 0..14) & 0xFF     ← NOT XOR
```

**Error responses:** packet[0] has bit 7 set (≥ 0x80). HR-log specifically returns sub-type `0xFF` in byte 1 when the requested day has no data.

**HR-log response layout (CMD 0x15):**

```
sub_type 0x00   header         — byte 2 = expected-chunk-count, byte 3 = range in minutes
sub_type 0x01   first chunk    — bytes 2..5 = unix ts (LE u32), bytes 6..14 = 9 HR bytes
sub_type 0x02..N data chunk    — bytes 2..14 = 13 HR bytes each
sub_type == size-1              — last chunk, parser yields HeartRateLog
sub_type 0x17 (23)              — end-of-day marker (today only)
sub_type 0xFF                   — no-data error for this day
```

**Day storage:** 288 slots @ 5-min interval = exactly 24h. Range byte tells you the interval; SR16 ships 5. 0 = no measurement, 1..254 = valid BPM, 255 = sentinel (tahnok normalises to 0).

**Reference repos:**
- `tahnok/colmi_r02_client` — full opcode table, parser patterns (Apache-2.0)
- `atc1441/ATC_RF03_Ring` — chip-level (BlueX RF03) + OTA flasher
- See commit 4ca4f01 in this repo for the protocol references captured at write time

## Caveat — SR16 may differ

The above is the **Colmi R02 protocol**. SR16 is almost certainly a re-skinned QRing (same BlueX RF03 + Telink) per Gadgetbridge's Yawell wearables doc, so the transport/packet/checksum/opcodes should be identical. **However:**
- The vendor service UUID may differ (`6E40FFF0...` vs some SR16-specific one)
- The command set may differ (e.g. 0xA00A vs 0x15 for HR log)
- The checksum math could differ (we use tahnok's `sum & 0xFF`, not Mats.coffee's XOR)

**This is what `enumerate_vendor.py` is for.** When the BLE-producer blocker is resolved (Forget device in System Settings → ring advertises again), run:

```bash
PYTHONPATH=src .venv/bin/python -m sr16_bridge.enumerate_vendor
```

It walks every service+characteristic, tags known UUIDs (Nordic UART, 0x180D, etc.), and writes to `char_inventory`. If SR16's vendor service is NOT `6E40FFF0-...`, the next step is editing the 3 UUID constants in `protocol.py` to match.

## Pitfalls captured (for future sessions)

### 1. `subprocess.Popen(...).wait(timeout=...)` is the right way to time-cap analyze.py
`gtimeout` / `timeout` are not on macOS by default. Don't block the whole session waiting on a slow Ollama response — use the Popen pattern from this session's verification.

### 2. `analyze.py --window-min 60` over 700 rows is slow
~700 rows / 60-min windows = ~12 windows = ~12 Ollama calls = 90s+. Use `--window-min 1440` (1 day per window) for batch ingestion. The 5-min window is correct for live-stream use only.

### 3. `source` column was missing from schema.sql — added via migrate()
Per session-3 pitfall #2, schema additions go in `migrate()`, not `schema.sql`. Both `analyze.py` and `history_sync.py` call `migrate()` on startup. Idempotent — re-runs are no-ops.

### 4. tahnok's checksum is sum, not XOR
Mats.coffee's RE blog has it as XOR — that's wrong for the Colmi/R02 family. The correct formula is `sum(packet[:15]) & 0xFF`. Verified via the live `battery.py` reference response: `\x03\x40\x00...\x43` → 0x03+0x40+0+...+0 = 0x43. Confirmed.

### 5. HR-log response sub_type 0x01 carries the timestamp in bytes 2..5 (LE u32)
Not in any of the blog writeups — only in tahnok's `hr.py:HeartRateLogParser.parse()`. Easy to miss if you only read blog summaries. The parser handles this correctly.

## Diagnosis

The ring is **deeply asleep** — possibly:
- **Battery fully depleted** (LiPo protection tripped if left at 0V too long)
- **Firmware stuck** in some pre-advertisement state (vendor app crash recovery?)
- **Charger contact issue** — even when placed on charger, the magnetic pogo pins may not be making contact
- **Physical damage** to the BLE antenna (unlikely but possible if recently dropped)

The Forget operation worked correctly (paired list is clean, BT log is empty for SR16). The blocker has moved from "HID auto-bond hides the ring from bleak" to **"ring is not transmitting at all"** — a fundamentally different problem that no software change on the Mac side can solve.

## What did NOT work and why

- **Forget → ring re-advertise:** forget cleared the pair record, but the ring never re-advertised afterward. Telink rings sleep aggressively and require a physical wake event.
- **`sr16_watch.sh 60`** twice: the script polls correctly, but the ring never woke during the polling windows. Either wake attempts weren't strong enough or the battery is too low to even transmit a wake-up advertisement.

## Path forward (for session 6)

The Mac-side code is now feature-complete. The blocker is hardware-side. Order of attempts:

1. **Hard-reset the ring via charger** (most likely to fix)
   - Place ring on charger; **verify LED pulses** (red/blue/green — vendor-specific)
   - If LED doesn't pulse after 30s on charger: contact issue → clean magnetic pogo pins with isopropyl alcohol
   - If LED pulses but ring still doesn't advertise: leave on charger for 1-2 hours for a real top-up, then re-run `sr16_watch.sh`
   - This is the path with highest success probability

2. **Charge for 30+ minutes** (if #1 fails)
   - Some Colmi-family rings need a long charge to recover from deep discharge
   - Then re-run `sr16_watch.sh 120`

3. **Vendor app rescue** (if #1 and #2 fail)
   - Reinstall the QRing app (or whatever vendor app shipped with the SR16)
   - The vendor app has proprietary "force re-pair" sequences that wake the ring
   - Pair with the app, sync once, then Forget again from System Settings
   - This gets the ring into a known advertising state

## Pitfalls captured (for future sessions)

### 6. PyObjC `retrieveConnectedPeripherals:` is the macOS API bleak doesn't expose
Bleak is a clean cross-platform wrapper, but it intentionally only sees advertising peripherals (the bleak docs are explicit about this). For already-connected peripherals, you need PyObjC direct CoreBluetooth. **Selector name in PyObjC is `retrieveConnectedPeripheralsWithServices_`** (not the no-argument `retrieveConnectedPeripherals` you'd expect from reading Apple's docs — that's a Swift convenience binding that doesn't expose in PyObjC). Argument must be a non-nil NSArray of CBUUIDs; pass `[]` to mean "any service".

### 7. macOS PyObjC CoreBluetooth delegate is an informal protocol
There's no Python class to inherit. PyObjC conformance is automatic — define methods whose Python names end in `_<param>` (PyObjC's auto-translation of Obj-C selectors like `centralManager:didConnectPeripheral:` → `centralManager_didConnectPeripheral_`). Don't call `objc.informal_protocol(...)` — that's for a different purpose (declaring protocols with selectors programmatically).

### 8. PyObjC methods named with trailing underscores take args; methods named without do not
`manager.retrieveConnectedPeripherals_(None)` → **TypeError: Need 0 arguments, got 1** (the Swift convenience binding is `retrieveConnectedPeripherals` with 0 args). Use `retrieveConnectedPeripheralsWithServices_([])` instead.

### 9. NSRunLoop + asyncio don't auto-interop
CoreBluetooth callbacks dispatch on the main NSRunLoop. The current `enumerate_cocoa.py` uses synchronous `time.sleep(0.25) + NSRunLoop.runUntilDate_(NSDate.dateWithTimeIntervalSinceNow_(0.25))` to pump the runloop. If you refactor to asyncio, you'll need an explicit runloop bridge (`asyncio.set_event_loop_policy(asyncio.DefaultEventLoopPolicy())` + manual runloop scheduling). Not worth the complexity for a one-shot enumerator.

### 10. Telink ring "asleep" is NOT the same as macOS "disconnected"
Session-3's root-cause analysis said: "ring is HID-over-GATT paired to macOS. bleak can't see it." That was correct for that session. In session-5, the Forget cleared the pair record, and now the ring is in a *different* state: not paired at all, and not transmitting. So the macOS side is doing the right thing (clean pair list, no auto-bond attempts). The problem moved entirely to the ring's hardware-side wake state. **The two are independent blockers and need independent fixes.**

## Pitfalls captured (for future sessions)

### 11. Hermes execute_code is blocked when running under cron-mode even for non-cron calls
Got `BLOCKED: execute_code runs arbitrary local Python (including subprocess calls that bypass shell-string approval checks). Cron jobs run without a user present to approve it.` — this fired on a normal interactive session because the runtime couldn't distinguish. Workaround: use `terminal()` directly. Note for any future automation: don't assume `execute_code` is always available.

### 12. The `nohup`/shell-background wrapper is rejected in favor of `terminal(background=true)`
Same runtime guard. Hermes tracks the process lifecycle via `background=true` + `notify_on_complete=true`. Don't try `nohup ... &` in foreground mode — it'll be rejected.

### 13. Daily note "coverage" labels show local HH:MM only — no date rollup across midnight
Currently the exporter's coverage line is `first_local → last_local`. If a day's data spans midnight (e.g. night-shift data at 23:50 → 00:10), the labels look misleading (it'll say `23:50 → 00:10` which looks like 25 minutes but is actually 24h+20min). Not a bug for normal daytime data, but worth knowing. If this matters, add a date suffix when the UTC dates differ.
