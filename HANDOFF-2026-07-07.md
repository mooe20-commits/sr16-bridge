## The BLE-producer blocker (next session starts here)

**Diagnosis (with evidence):**
- `system_profiler SPBluetoothDataType` shows the SR16 in the **Connected** section with `Minor Type: Mouse`, `Services: 0x400000 < BLE >`, address `38:00:00:00:DE:90`
- `blueutil --paired` shows it as paired + connected (master) + classified as a mouse
- `blueutil --unpair 38-00-00-00-de-90` runs cleanly but the OS keeps it in `Connected` (HID auto-bonding)
- `blueutil --connected` continues to show it
- `log show --predicate 'subsystem=="com.apple.bluetooth"'` shows `Server.HID isLowLatencyBLEHID`, `switchLEHIDsConnectionInterval`, manufacturer 0x06D6 (Telink) ✓
- `bleak.BleakScanner` does not see it (100s scan returns 0 SR16 sightings even with ring on finger)
- macOS bt log shows the daemon `Monitor Device Found: CBDevice 36BE6673-1486-2E90-38E9-3E097DB4CC43` events with Telink manufacturer data — confirming the ring IS active, but bleak's scanner path ignores connected-only peripherals

**Conclusion:** The ring is HID-over-GATT paired to macOS. The OS HID-CL auto-bonding silently re-binds it after every disconnect. **It does not advertise while connected**, which is normal for paired BLE peripherals. bleak's `BleakScanner` only sees advertising peripherals → ring invisible.

**User-visible fix attempts that DID NOT work:**
1. `blueutil --disconnect` — re-bonds instantly
2. `blueutil --unpair` — re-bonds instantly
3. Ring on/off, app disconnected, phone BT off — no change in advertisement behavior

**Fix paths to try in the next session (priority-ordered):**

1. **System Settings → Bluetooth → right-click SR16 → Forget This Device**, then re-pair (if needed) explicitly through macOS Bluetooth settings, **not** the phone. Once fresh, the ring will advertise again and bleak can see it. REPAIR ONLY if necessary — once forgotten, the ring should advertise in normal pairing mode. Time: ~5 min.
2. **PyObjC direct-CoreBluetooth path:** `from CoreBluetooth import CBPeripheral` and ask the macOS daemon for the already-connected peripheral. bleak doesn't expose this, but PyObjC does. Bypasses the advertising requirement entirely. Time: ~30-60 min to write + test.
3. **BLE Controller restart:** `sudo killall bluetoothd` (or equivalent on macOS 15.7 — may need `sudo ifconfig bt0 down/up` or similar). Forces HID auto-bonds to reset. RISKY — this also drops audio devices. Time: ~5 min to try.
4. **Reboot Mac:** clean slate. Time: 2-5 min for it to come back, plus re-pair overhead.

**Recommended first attempt:** path #1 (Forget via System Settings). If that fails to make bleak see the ring, fall back to #2 (PyObjC).

## Pitfalls captured for the next session

### 1. BLE producer: SR16 is paired as HID Mouse (session 3, BLOCKER)
See diagnosis above. The path forward is in the bullet list. Two structural notes:
- bleak cannot see connected, non-advertising BLE peripherals. Period.
- The session-1 "ring went to sleep mid-enumerate" pitfall was actually this same root cause, not a Telink sleep-after-connect bug.

### 2. sqlite ALTER TABLE is not idempotent (2026-07-07, FIXED)
`ALTER TABLE hr_readings ADD COLUMN analyzed_at` fails with `duplicate column name` on second run. Fixed via `migrate()` in each command using `PRAGMA table_info` to check before applying. **Future schema additions MUST go in `migrate()`, not in schema.sql** — schema.sql is for `CREATE TABLE IF NOT EXISTS` only.

### 3. Python sqlite3.Cursor uses `.lastrowid`, not `.lastrow` (2026-07-07, FIXED)
Standard library typo that's easy to repeat. We use `.lastrowid` in `analyze.py`.

### 4. Telink manufacturer ID is 0x06D6 = 1750 (2026-07-07)
Confirmed via bt log. Useful next time we need to identify rings in any scan output.

### 5. cron must live in `~/.hermes/scripts/` (2026-07-07)
`cronjob create ... script=...` rejects paths outside `~/.hermes/scripts/`. Symlinks don't satisfy "must not escape via traversal" check either. Copy, don't symlink. Also: `no_agent=true` requires `prompt` to be omitted.

### 6. `deliver='origin'` from a local-TUI cron does NOT show up in this chat (2026-07-07)
Per platform rules: local-only cron output is saved (viewable via `cronjob list`) but NOT delivered back into the TUI. For real "tell me what happened" notifications, use `deliver='telegram'` (or another gateway-connected channel).

## New architectural decisions (session 3)

### 1. analyze.py is producer-agnostic
`analyze.py` only cares that rows exist in `hr_readings` with `analyzed_at IS NULL`. Whether they came from `hr_live.py` (real BLE), `history_sync.py` (vendor RE), `history_ingest.py` (file import), or a synthetic test insert — it doesn't matter. This means the gateway is **unblocked by the BLE-blocker**. As soon as *any* source writes hr_readings rows, the analyzer picks them up.

### 2. analyze.py is idempotent via the `analyzed_at` column
Re-running on already-analyzed rows is a fast no-op (partial index `hr_readings_unanalyzed` finds the new ones). Cron can run at high frequency safely.

### 3. Ollama model is pinned
Per USER profile (memory), the Twitter-HERETIC model is the user's local default. analyze.py defaults to `Qwen3.5-9B-Claude-4.6-HighIQ-HERETIC:latest` and accepts `--model` to override. **Never** substitute Ministral without an explicit user direction (memory rule).

### 4. Cron is `no_agent=true` + `deliver='telegram'` (silent-watchdog pattern)
Script decides whether to emit output (silent when idle, summary when new). No LLM tokens per cron tick. Telegram receives only when there's something to say.
