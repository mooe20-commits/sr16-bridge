## What we tried, in order, this session

### 1. `multi_notify_probe.py` — 256-opcode sweep to FF02 (FF00 transport)
**Result: zero notifies on FF01 or 0BC2.** All 256 single-byte writes sent
cleanly to FF02 (write-ack each), but the SR16 ignored every single one.

**Verdict:** SR16 does NOT respond to 16-byte single-command packets on the
FF00 transport. The Colmi R02 opcode table (0x01 set_time, 0x03 battery,
0x15 hr_log, etc.) does NOT apply to the SR16.

### 2. `grab_connected.py` — direct attach via `retrieveConnectedPeripherals`
**Result: returns 0 devices.** macOS has the ring classified as an HID Mouse
(major service class HID) and the GATT connection is owned at the HID layer.
CoreBluetooth can't see it. **No software trick on the Mac can bypass this.**

### 3. `probe_a00a.py` — write to A00A:B002, listen on A00A:B003 (A00A transport)
**Result: zero notifies on B003.** Writes accepted (write-ack), B003 NOTIFY
ON, but the ring never sends anything back.

**Verdict:** SR16 does NOT respond to 16-byte single-command packets on the
A00A vendor transport either.

### What this rules out
- The protocol is NOT a 16-byte opcode+subdata+checksum shape (Colmi R02)
- 268 distinct opcodes tested across two transports — none triggered any
  response
- The ring DOES have correct GATT plumbing: writes return ack, notify
  subscriptions return success — the ring's firmware is choosing not to
  respond, not the BLE stack failing
- Vendor service UUID IS `0xA00A` (confirmed via service discovery), but
  the protocol on it is not what we assumed

### What this doesn't rule out (still open)
- **BLE encryption / LTK pairing** — most likely. Telink rings commonly
  require the link to be encrypted with the LTK from a prior pair. Unpaired
  hosts get GATT connect + services + chars, but the firmware rejects
  writes. This is the standard "ring only talks to its vendor app" pattern.
- **Variable-length or auth-header packet format** — possible but unlikely
  given 268 byte-1 values tested
- **The "real" control channel is 0BC0** — possible but lower probability;
  0BC1:0BC2 are read-only sub-channels and not a typical control pair
- **A completely different vendor service UUID** — unlikely; the vendor
  dump from the ring's firmware name would not match A00A otherwise

## The conclusion — RE requires nRF Connect sniff

Software-only RE from the Mac side is now blocked. We've exercised every
practical angle: two transports, full opcode sweeps, all notify chars
subscribed. The ring's firmware is **deliberately not responding** to
unauthenticated writes.

**The next move must be nRF Connect on iPhone** (free app). Pair the ring
with the QRing / vendor app first — that establishes the LTK encryption.
Then in nRF Connect's packet capture, observe the actual command bytes
the vendor app sends. The opcode table for the SR16 is right there in
those packets.

**Order of operations for session 8:**

1. **Install nRF Connect on the iPhone** (App Store, free, Nordic Semiconductor).
2. **Pair the ring with its vendor app first** (QRing / whatever shipped
   with the SR16) on iPhone. This establishes the BLE bond + LTK.
3. **In nRF Connect → Bonded devices → SR16** → enable "Record traffic"
   → start the vendor app's history-sync → see the actual command bytes.
4. **Capture the wake-up handshake bytes** (the first exchange that
   unlocks the ring's command surface).
5. **Patch protocol.py** with the discovered opcodes.
6. **Run `history_sync --days 1` against the now-bonded ring.**

We also have a half-decent fallback that would still let the SR16 be
useful WITHOUT decoding the protocol:

**Fallback: use the standard Heart Rate Service (0x180D).** Every
Bluetooth-LE ring must implement it. If the SR16 advertises 0x180D
(it does — confirmed in the session 6 log: `advertised services: 0xA00A,
0x180D`), and we can subscribe to its HR measurement char, we get live
HR notifications regardless of the vendor protocol. This is the
"quick win" path — it's the standard profile, not vendor-specific, no
vendor opcode RE needed.

The question: **is 0x180D actually exposed after connect in the SR16?**
Session 6.5 inventory only showed the 3 services the GATT walk revealed
(FF00, A00A, 0BC0). 0x180D was advertised but not seen as a service in
the discoverServices callback. That might just be because our scripts
filtered to FF00 only — they didn't walk the full service tree. **Worth
checking in session 8.** If HR is on a standard 0x180D char, we can
just `subscribe → receive 2-byte HR notifications → write to
hr_readings → done`, completely skipping vendor protocol RE.

## Pitfalls captured (additions to the handbook)

### 19. SR16 ignores all 16-byte Colmi-R02-style writes (2026-07-08, RULES OUT tahnok/colmi)
Wrote 256 different single-byte opcodes (0x00..0xFF) to BOTH FF02 (FF00-RX)
and B002 (A00A-RX). All writes returned write-ack. Zero notifies on FF01,
0BC2, B003. **The SR16 firmware rejects unpaired/no-encryption writes
entirely**; it does not implement the Colmi 16-byte command surface.

### 20. macOS HID-Mouse classification blocks CB attach permanently (2026-07-08)
`retrieveConnectedPeripheralsWithServices_([])` returns **0** for any device
the OS has claimed at the HID layer (mouse, keyboard, etc.). The only escape
is disconnecting from System Settings AND racing a CB connect before macOS
re-bonds the device. The race window is ~5-30s depending on OS activity.

### 21. CCCD code 10 "attribute could not be found" on B002 + 0BC1 (2026-07-08)
Subscribing to a char that lacks a 0x2902 descriptor returns
`CBATTErrorDomain Code=10`. The char still works for write/read — it just
can't deliver notify. Skip on subscribe failure, continue to next char.

### 22. CCCD exists on FF01, 0BC2, B003 — these are the only valid notify
chars (2026-07-08). For notify-only investigation, target these three.
