## TL;DR — session 9 status

**BREAKTHROUGH.** The Android HCI snoop worked. We have the actual vendor protocol bytes.

- **Vendor protocol is `0xAB`-prefixed, NOT Colmi R02.** `protocol.py` (the 304-line module from session 5) is wrong about the transport and must be rewritten.
- **Vendor char handles discovered:**
  - `0x003e` = WRITE (phone→ring) — RWfit sends 78 commands to this handle in 90s
  - `0x0040` = NOTIFY (ring→phone) — ring sends 78 notifications back, exact mirror
  - `0x0037` and `0x0041` are WRITE_REQUEST (HID/Hogp-related, 1 write each — CCCD writes)
- **Packet header:** `0xAB 0x01 LEN CMD [data...]`
  - 0xAB = vendor magic
  - 0x01 = command direction (0x11 = notify/response)
  - LEN = payload length (1 byte)
  - CMD = opcode
- **Opcodes seen in this capture:**
  - Writes (phone→ring): 0x03 (75), 0x04 (1), 0x05 (1), 0x09 (1)
  - Notifies (ring→phone): 0x03, 0x04, 0x05, 0x06, 0x13, 0x43, 0x53, 0x67, 0x73, 0xa3
  - The big payloads (0xA3=169 bytes, 0x67=109 bytes, 0x73=121 bytes) are history data blocks
- **Galaxy side:** `com.rw.revivalfit` (NOT `com.koepovksmart.rwfit` — earlier greps missed it; the package path is different). ACL up to `38:00:00:00:DE:90 [LE] SR16 (Hogp)` for 10+ min during sync.

### 6. The protocol itself
- All 78 vendor writes start with `0xAB 0x01`, all 78 notifies with `0xAB 0x11`.
- LEN byte gives the payload length.
- The CMD byte is the opcode; the data after is opcode-specific.
- 0xA3 notify (169 bytes) and 0x67 (109 bytes) are almost certainly the bulk history data — exactly what we want for `history_sync.py`.

## What this rules out

- The Colmi R02 model in `protocol.py` is **wrong** for this ring. The 0xAB prefix is not the Colmi Nordic UART transport. The 0x15 HR-log read command is not present. The 16-byte fixed packet shape is not present (packets range from 9 to 169 bytes).
- 0xA00A service UUID is still in `protocol.py` as the only "vendor" service — but the actual writes/notifies we captured went to `0x003e`/`0x0040` (which are ATT handles, not service UUIDs). Need to re-enumerate the phone-side service discovery to find the owning 128-bit service UUID for handles 0x003e and 0x0040.

## What session 10 should pick up

**The protocol is mostly cracked, but the application layer still needs to be figured out.** Goal: read 288 HR samples from the 0xA3 / 0x67 / 0x73 notify payloads.

### Step 1 — Re-enumerate services to find 128-bit UUID for handles 0x003e/0x0040 (15 min)

The snoop captured the data exchange but not the service-discovery phase in enough detail. Either:
- Trigger another sync with the bugreport capturing the *start* of the connection (not the middle), or
- Use `tshark -Y "btatt and (btatt.uuid128 or btatt.uuid16)" -V` to extract any UUID fields that show up in read-by-group-type responses around frames 367-394 (where the service discovery happened).

Once we have the 128-bit UUID for 0x003e/0x0040, repoint `protocol.py`'s `UART_*_CHAR_UUID` to those.

### Step 2 — Decode the 0xA3 / 0x67 / 0x73 payloads (1-2 hours)

These are the bulk data blocks. Compare against:
- `0xA3` (169 bytes): 4 bytes header (ab11 00a3) + 165 bytes payload. 165 = 11 × 15 = 11 × (1 BPM + 14 byte timestamp?) — guess, need to validate.
- `0x67` (109 bytes): 4 bytes header + 105 bytes payload. 105 = 7 × 15 (same pattern).
- `0x73` (121 bytes): 4 bytes header + 117 bytes payload. 117 = ~9 × 13 (different shape).

Most likely structure: 4-byte unix timestamp + 1-byte BPM repeated N times, matching the 5-min slot grid (288 slots / 24h).

### Step 3 — Replace `protocol.py` Colmi R02 model with the 0xAB vendor model (1 hour)

- New `UART_SERVICE_UUID` (the 128-bit UUID from step 1)
- New `UART_RX_CHAR_UUID` (handle 0x003e → 128-bit)
- New `UART_TX_CHAR_UUID` (handle 0x0040 → 128-bit)
- New `make_packet(cmd, data)` that emits `0xab 0x01 LEN CMD [data]` (no checksum — snoop shows none)
- New parsers for each opcode's payload shape (start with 0x03 = battery?, 0x05 = ?, 0x09 = ?)

## Pitfalls captured (additions to handbook)

### 26. tshark 4.6 field names use `bthci_acl.*` not `btle.*` (2026-07-08)

`-G fields | grep bd_addr` is the right way to discover the right name in your tshark version. The names changed between Wireshark 3 and 4. Symptom: tshark rejects `-e btle.bd_addr` with "Some fields aren't valid".

### 27. Samsung One UI 5/6 snoop is gated by `mSnoopLogSettingAtEnable`, not `persist.bluetooth.btsnoopenabled` (2026-07-08)

The shell user can't read or set `persist.*` SELinux-protected props. But the BT snoop still works fine — the toggle in Dev Options sets the BT-manager-side setting, and `bugreport` captures the active snoop log. To verify the toggle took: `adb shell dumpsys bluetooth_manager | grep SnoopLogSettingAtEnable`. Expected: `mSnoopLogSettingAtEnable = full`.

### 28. RWfit package is `com.rw.revivalfit`, not `com.koepovksmart.rwfit` (2026-07-08)

`pm list packages | grep rwfit` returns nothing on this install. `dumpsys window | grep mCurrentFocus` reveals `com.rw.revivalfit/com.example.test.ui.testui.TMainRingActivity`. If you're hunting for the package, use the focused-window trick instead of pm-grep.

### 29. ADB bugreport takes 3-5 min on Galaxy S10e (2026-07-08)

`adb bugreport` is wrapped in Java and runs `dumpstate` which is slow. The `bugreportz` binary on the device is faster (skips some categories) but only works if a previous dump isn't already running. `ps -A | grep dumpstate` is the way to check.

### 30. `dumpsys bluetooth_manager` shows `(Connected)` lines for live ACLs (2026-07-08)

Look for `(Connected) 38:00:00:00:DE:90 [LE] SR16 (Hogp)` in the output. This is the moment to take a bugreport — the snoop log is actively capturing packets at this point.

### 31. The SR16 is HID-over-GATT (Hogp) on the phone side too (2026-07-08)

The phone side sees the ring as `Hogp`, not just "LE" — confirming the macOS-side pitfall P1 (HID auto-rebond) is intrinsic to the ring's advertised profile. The vendor transport rides on top of the Hogp GATT chars, not a separate service.
