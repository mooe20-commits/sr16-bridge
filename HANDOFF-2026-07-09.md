## TL;DR — session 8 status

Even after forgetting the HID bond, the ring's radio is off more than on, and we have no Mac-side mechanism to keep it awake (would need to be already-connected to write its wake char — chicken-and-egg).

The Galaxy is the right host for sniffing because RWfit already runs there, has the LTK, and the Android Bluetooth HCI snoop log captures every ATT/GATT packet — including the vendor opcodes that have eluded us for 7 sessions.

**Consumer pipeline (SQLite → local AI):** unchanged and green on synthetic data.

## What we tried in session 8

### 2. `sudo killall bluetoothd` (you executed in your terminal)
- Kills the OS BT daemon → ring re-advertises briefly

- **Ruled out**: daemon-kill race is too tight for CB to win

### 3. Forget device in System Settings
- This is the correct fix for the HID auto-rebond

## What this rules out

- The 0x180D HR Service quick-win path on Mac is **architecturally blocked** by ring firmware sleep behavior, not by protocol or encryption
- All known macOS-side techniques to keep a sleeping peripheral awake (killall bluetoothd, disconnect, forget) have been tried
- A working Mac-side 0x180D solution would require either:
  1. A way to keep the ring's radio on (no documented API; vendor-only firmware control)
  2. The ring to be plugged in / always-on (not how it ships)
  3. Pre-existing bonded connection (would need RWfit to release its bond first — defeats the point)

## The pivot — Android HCI snoop

**Standard pattern (Gadgetbridge wiki, Oura RE, every other ring RE):**
1. Enable Developer Options on the Galaxy (tap Build Number 7x)
2. In Developer Options: enable "Bluetooth HCI snoop log" + "USB debugging"
3. Toggle Bluetooth off→on (forces log to start fresh)
4. Open RWfit → trigger a sync (this is the action we want to capture)
5. Pull the snoop log: `adb bugreport` (zip includes `FS/data/log/bt/btsnoop_hci.log`)
6. Open the log in Wireshark → filter on the SR16 MAC/UUID → see every ATT write/read
7. Decode the opcode table from the writes → patch `protocol.py`

**What we get for free:**
- The wake-handshake bytes we couldn't find via opcode sweep — visible as the first write after connect
- The encryption/LTK negotiation (or proof that it's not happening) — visible in the SMP (Security Manager Protocol) exchange
- The history-sync command structure — RWfit's sync action is exactly the one we want to replicate
- Confidence that the protocol is decryptable (Gadgetbridge's HPlus protocol, Oura, Colmi R02 all RE'd this way)

**What we need on the Mac:**
- Wireshark (free, GUI) — for visual protocol decode
- `adb` (Android Platform Tools) — for `adb bugreport`

Neither is installed. Both are brew-installable: `brew install --cask wireshark` and `brew install --cask android-platform-tools` (or `brew install android-platform-tools` for adb only).

4. Connect phone to Mac via USB
5. `adb devices` should show your Galaxy (you may need to tap "Allow USB debugging" on the phone)

### Step 3 — capture sync traffic (5 min)
1. **On the phone:** open RWfit → tap the sync / connect button
2. **On the Mac:**
   ```bash
   mkdir -p ~/health/sr16_captures
   cd ~/health/sr16_captures
   adb bugreport sr16_sync_$(date +%Y%m%d_%H%M%S)
   # when complete:
   unzip -o sr16_sync_*.zip 'FS/data/log/bt/btsnoop_hci.log' -d ./extracted/
   ```
3. The `btsnoop_hci.log` file is your raw capture. Wireshark reads it natively.

### Step 4 — analyze (15-30 min)
1. `open extracted/FS/data/log/bt/btsnoop_hci.log` (Wireshark opens it)
2. Apply display filter: `btatt.opcode == 0x12 || btatt.opcode == 0x52`
   - `0x12` = ATT Write Request
   - `0x52` = ATT Write Command
3. Look for the SR16's MAC/UUID in the Source/Destination columns
4. The first few writes after connect are the wake-handshake — these are the bytes we couldn't find via opcode sweep
5. Note the destination characteristic handle (a small integer like 0x0012) — that's the FF02 (FF00 service) or B002 (A00A service) write char
6. Right-click any interesting packet → "Copy as Hex Stream" → paste into the protocol doc

### Step 5 — patch protocol.py (15-30 min)
1. Once we have the opcodes, update `src/sr16_bridge/protocol.py`:
   - `UART_SERVICE_UUID` is already set to A00A from session 6
   - Add the discovered RX char handle and TX char handle
   - Add the wake-handshake bytes as a function `wake_ring(payload)`
   - Add the sync-history command as `read_history(start_ts, end_ts)`
2. Add tests in `tests/test_protocol.py` (the function should encode known inputs and assert the byte layout)
3. Run `PYTHONPATH=src .venv/bin/python -m sr16_bridge.history_sync --days 1` against the live ring

## Pitfalls captured (additions to handbook)

### 23. macOS auto-re-grabs SR16 as HID Mouse within 1-2s of any disconnect (2026-07-09)
`sudo killall bluetoothd` works but bluetoothd restart + HID re-bond completes before any third-party scanner can attach. Forget device in System Settings is the only durable fix on the Mac side. Even with Forget, the ring's radio is asleep >90% of the time, so the scan window is a separate problem (pitfall 24).

### 24. SR16 ring firmware aggressively sleeps its radio (2026-07-09)
After wake (charger pulse / tap), the ring advertises for ~20-40s then radio-off again. Subsequent wake requires another physical interaction. We have no way to keep it awake from the Mac side. Standard 0x180D subscribe on Mac is therefore not a viable path without first RE'ing the vendor wake-extension command — which requires sniffing the vendor app traffic (Android HCI snoop, see session 9 plan).

### 25. bleak on macOS returns BLE UUID form for device address, blueutil returns MAC form (2026-07-09)
A device filter that hardcodes MAC form (e.g. `38:00:00:00:DE:90`) will reject all candidates. Accept both forms in the filter, or use bleak's UUID form consistently. Symptom: `BleakScanner.discover()` returns the device, but a filter on MAC form silently drops it.
