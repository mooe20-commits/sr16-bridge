# sr16-bridge Handoff — 2026-07-13 (session 14)

Read this first when picking up sr16-bridge in a new session.

## TL;DR

**Goal "data out of the ring" → SHIPPED end-to-end via reverse-engineered protocol + Android HCI snoop → SQLite ingest.**

We learned the ring speaks the same 0xAB protocol as session-9 (RWfit-paired original), but **with a different firmware that uses markers 0xE631/0xE731 (vs the older 0xE031/0xE131)**. Both firmware variants expose the same opcodes and write catalog — only the marker bytes differ. The previously-built decoder (`src/sr16_bridge/decode_0ab.py`) already handles the new markers; we just had to relax the day-summary skip filter.

What we did this session:

1. **Path A (RWfit DB pull)** — blocked. Android 12 deprecates `adb backup`; APK not debuggable; `run-as` refused; no `su`.
2. **Path A fallback (in-app export)** — RWfit has no "Visitor"/guest-mode export. Without an account the export options don't exist.
3. **Path D — Gadgetbridge** — installed via F-Droid, paired with the ring (manual device-type pick because SR16 isn't in the autodetected device list; chose closest Colmi R02). Sync **hung visibly but worked** under the hood — full BLE traffic captured by the on-device snoop buffer (mSnoopLogSettingAtEnable = full).
4. **Captured a fresh bugreport** while Gadgetbridge was probing the ring → `~/health/sr16_captures/sr16_gadgetbridge_20260713_123608.zip` (60 MB), extracted `btsnoop_hci.log` (1.79 MB).
5. **Decoded 701 ring→phone notifications** from the snoop. Confirmed: same protocol as session-9, new marker bytes, same opcodes and op-byte timings. Found 25 unique 0xA3 (today's-hourly) packets + 8 0x43 older-day-16B + 8 0x6B older-day-8B + 19 0x67 byte-grid.
6. **Wrote `src/sr16_bridge/ingest_snoop_to_db.py`** — ingester that:
   - Reads a `btsnoop_hci.log` via tshark
   - Decodes each notify through the existing `decode_0ab.py`
   - Dedupes per-record by (cmd, marker, val16, data)
   - Inserts 16B records into `a3_hourly` (~40 rows from this snoop)
   - Skips the 8B older-day u32 records for now (new table wanted)
7. **Built `a3_hourly_rollup` SQLite view** — per-hour rollup that picks the row closest to each hour boundary (handles the P34/P51 retransmit-dedupe issue cleanly). 31 rollup rows: 13 hours from 2026-07-10 (session-9 capture), 18 hours from 2026-07-13 (today, this session).

## How to run end-to-end today

```bash
# 1. Enable snoop on phone (one-time per session): Developer Options → "Bluetooth HCI snoop log" → on
# 2. Generate BLE activity on phone (open RWfit and tap Sync, or any app that touches the ring)
# 3. Trigger bugreport
adb bugreport ~/health/sr16_captures/sr16_<name>.zip
# 4. Extract
cd ~/health/sr16_captures
unzip -o sr16_<name>.zip 'FS/data/log/bt/btsnoop_hci.log' -d sr16_<name>_extracted/
# 5. Ingest
cd ~/projects/sr16-bridge
PYTHONPATH=src .venv/bin/python -m sr16_bridge.ingest_snoop_to_db ~/health/sr16_captures/sr16_<name>_extracted/FS/data/log/bt/btsnoop_hci.log
# 6. View rollup
sqlite3 ~/health/sr16.db "SELECT * FROM a3_hourly_rollup ORDER BY date_local DESC, hour_utc;"
```

## Reference: ground-truth activity for the 2026-07-13 snoop

The snoop was captured between ~12:35 and 12:38 local (EEST = UTC+3, so 09:35-09:38 UTC). The ring was actively syncing with Gadgetbridge at that moment. The val16 timestamps in the 0xA3 packets are mostly 17:14 UTC and earlier — meaning the ring's current-day buffer goes from 00:00 UTC (sometime) up to ~17:14 UTC = up to ~20:14 local time. So this snoop contains nearly a full day of activity.

## Pitfalls captured this session

- **P53 (new)**: 0xE631 marker for "current in-progress hour" rows on the SR16 firmware-with-display variant. Day-summary marker on this firmware is **0xE731, NOT 0xE131**. Same vendor, different firmware. The README/skill rewrite is pending.
- **P54 (new)**: SR16 firmware-with-display variant retransmits 0xA3 in-progress hour records multiple times across the day, with **different val16 timestamps for the same data**. The per-record dedup by `(marker, val16, data)` doesn't catch this — use the per-hour rollup view that picks the row with val16 closest to the hour boundary.
- **P55 (new)**: Android HCI snoop size grows significantly with Bluetooth activity. Our 1.79 MB snoop captured ~3 min of Gadgetbridge probing. For long-term collection the buffer rolls over (P28); for one-shot captures the bugreport pattern works fine.
- **P56 (new)**: `adb bugreport` produces 60-100 MB zip in ~5 minutes. The extracted `btsnoop_hci.log` is the only file we care about; the rest can be discarded to save disk.
